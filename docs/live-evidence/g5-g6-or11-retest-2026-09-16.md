## Task 3 — G6 PA2/PA3 `err:1`: state-dependent messages, not an app-version gate

Against the newest WCF order **1058423434 / part 1076907159** (cancelled at the

Key finding: the `err:1` **messages are order-state-dependent, not
version-gated** — for a cancelled WCF order the messages become
"Objednávka se zadaným ID neexistuje" (PA2) / "Objednávka nebyla nalezena"
(PA3), while the 2026-09-08 re-test against the still-open order 1056808137
recorded "Faktura se zadaným ID neexistuje" / "Aktualizujte prosím aplikace".
In every state the exact latest app UA (2026.17.0/459, the newest release)
does not change the result. The mobile after-order family's order/invoice
lookup therefore covers restservice-pipeline orders only — server-side
semantics, `err:1` conclusive across UA variants, auth variants, paymentIds
and order states. PA3 was fired only under the PA2-err:1 safety gate (no
charge possible); the gate held in every run.

## Task 4 — OR11 cancellation on 1058423434: 2026-09-15 anomaly resolved

| Step | Call | Result |
|---|---|---|
| 1 | `GET /api/anonymous/v1/orders/1058423434` (before) | 200, part status **"Objednávka byla zrušena"**, phase 4, `isLocked:false` — the 2026-09-15 cancellation had taken effect |
| 2 | `PUT /api/v1/orders/1058423434/0A8697U8EU43B71A25B3bOB215/parts/1076907159/cancellations` (identical body) | **HTTP 202 with an empty body** (`json:null` = the JSON.parse of an empty 202 body) |
| 3 | order re-read (after) | "Počkejte prosím" / "Zpracováváme změny", `isLocked:true`, phase 3 — the re-issued PUT re-triggered the cancellation processing |
| 4 | `GET /api/v1/orders/1058423434` (authenticated, Bearer) | HTTP 404 — the WCF port-1002 service does not serve `/api/v1/orders/{id}`; the anonymous read (OR3) is the working order-detail route |

Follow-up reads (no mutation, `or11-cancel-followup-2026-09-16.json`):
immediately and after 45 s the part status is again **"Objednávka byla
zrušena"**, phase 4, `isLocked:false` — the re-triggered processing resolves
back to the cancelled state.

Resolution: the 2026-09-15 "null" was **202 Accepted with an empty body**
(async cancellation accepted, response body intentionally empty) and the
cancellation **did take effect** (cancelled, phase 4). Re-issuing the PUT is
idempotent-safe (re-submits the cancellation; the order re-enters
"Zpracováváme změny" and resolves back to cancelled). Row OR11's 202-accepted
semantics stand; the anomaly is a documentation gap, not a behavior change.
